# 当前已选视频的真实媒体提前准备

用户要求继续把可预处理的工作提前完成，不再以“空播放器未准备真实媒体”作为停止理由。按当前明确要打开的视频执行，不新增首页候选批量预载或改变选流。

证据：旧版4条样本的ui.mount.request到source.open.begin分别129/20/91/17ms。快速控制样本创建播放器/输出约104ms。现有路径在playerInit中先等待路由，再在_createVideoController中等待页面endOfFrame，之后才open真实媒体。

候选SOURCE_EARLY_PREPARE将真实媒体以play:false打开，与页面路由/挂载准备重叠；保留同一个Player、原输出、EDL、选流、自动播放和显示门槛。两个准备都完成且请求仍有效后才进入原播放流程。预期覆盖页面前置等待，约17–129ms是历史可见窗口，不预先宣称能省掉API或整段解码等待。

此处是点击后、地址确定后的提前准备。它允许媒体连接/识别/解码在UI等待时进行，不假称为点击前已解码，也不使用假视频预播或新的转发层。

先运行source_preparation_check.dart验证真实加载可以先于页面完成、播放不会先于页面、取消不会让两个播放器写入竞争、页面/媒体失败仍能释放队列。此前控制源和新候选分别构建，两个包都开启已有Player待命，关闭深度trace，唯一区别为SOURCE_EARLY_PREPARE。构建顺序执行且模拟器关闭，保留内存门槛；不与相册编译并行。

定向验证按A/B/B/A四条冷App首视频，各35秒，一台原AVD同一次启动；使用BV15BJX6dEoR/CID42790290231及现有App内URI搜索提交入口。核对原始WebM指针、媒体真实运动、后续连续性和阶段记录。source.open.accepted为实际open返回，source.open.return在候选中为媒体打开和页面准备都完成；不得用后者混称实际取流开始。

必须记录失败和慢样本，不为等好结果重复同视频。没有明确画面收益就不扩展十视频、不将此候选作为生效优化；有明确收益且连续播放正常后再验证至少十个不同视频及返回/切换等功能。深度诊断旧样本不能混入本次速度对照。

扩展阶段：固定videos.json的0–9，各包每视频一次，偶数视频候选先、奇数视频对照先。同一新AVD启动，两包不重新构建。首个输入突发被IME截断（CID42781444而非42781444806）导致-404，保留失败录屏，不计入速度。之后统一分段注入URI并在计时前检查完整搜索框，预检仅操作搜索输入、未预载真实媒体。因为预检增加了未计时的搜索页准备时间，该组与此前四条单列，不直接合并均值。为同条件覆盖完整10视频，index5也只补一个新协议配对，不再重复四条ABBA。
