# 首次续播耗时归因，第54轮（2026-10-31）

这里回答“这些时间到底发生了什么”。只使用 session98 同一次记录拆分，不拼接其他轮次的最好数字。这是新增应用/原生监听、8秒系统跟踪、12秒宿主快照的重型诊断；不与轻监听 release 测速比较，不宣称优化收益。

固定条件：App 重启后第一次点击，直接续播到61.5秒。APK SHA256 `b7ebe2d66922ec90e34dba432104941ef9be902bd67d2f1f1a493712a3bfc32b`。播放实现保持第53轮，新增的是诊断。

|---|---:|---|
| 0–1.254秒 | 1.254秒 | 处理输入、获取播放地址、进入媒体打开。其间0.231–1.165秒存在全模拟器调度空窗；不能把这1.254秒全部称作网络请求耗时。 |
| 1.254–1.949秒 | 0.695秒 | 打开音视频媒体、解析封装、准备解码。其中原生媒体打开调用0.656秒，调用线程主要等待媒体打开线程。 |

## 已定位的具体机制

1. **全模拟器的约一秒空窗重复出现。** 96、97、98三条分别约1.116、0.929、0.933秒，四个虚拟CPU在同一时段均无调度切换。98宿主采样显示前半段两个线程持续运行，后半段大量线程等待。这不是仅凭UI帧耗时猜测。仍缺宿主调用栈和锁主，因此不能说已证明由某一个图形调用、某把锁或Windows抢占造成；也不能把该时长从测试总时间直接扣掉。

2. **新解码器先验证10个输出帧的时间戳。** 原生源码把 `has_broken_packet_pts` 初始化为-10，每个解码输出使其递增，到0才允许进入精确续播的提前丢弃分支。97与98的实际记录都显示最早15个送包的drop标志为0，后面才开始跳过，最终各跳过16包。还需要直接记录该变量，区分时间戳验证与其他限制对每个包的具体作用；不会先取消这个检查再猜测收益。

3. **系统编解码器调用主要在等响应。** 98中创建205毫秒，调用线程运行约5毫秒；启动204毫秒，运行约0.13毫秒。97的Binder关联进一步显示输出缓冲区分配、图形服务查询等调用。初始化耗时不能直接称为CPU解码耗时。

4. **首帧生成后仍有封面放行等待。** 98中两组属性读取各自并行等待约80和96毫秒，之后约54毫秒达到稳定条件；首帧到第一组提交前仍有约196毫秒的事件交付间隔未完全归因。并行属性等待不重复相加，不取消来源核验来制造更快数字。

## 排除与证据边界

97中播放API解压0.148毫秒、UTF-8转换0.182毫秒、JSON提交0.116毫秒、Cookie处理0.097毫秒、模型转换0.118毫秒；这些具体操作不是那一秒长停顿的原因。98的对应操作也远短于该空窗。HTTP头/正文监听记录的是应用观察到的时刻，遇到全模拟器停顿时不能直接等同于网卡到包时刻。

新监听82组Dart begin/end配对，原生scope配对，系统跟踪未报告非零错误/丢失统计。该事实不等于监听无开销。宿主快照100毫秒一次，单次中位15.6毫秒，最多40.7毫秒；它不是无损调度追踪，时钟对齐约±26.9毫秒。所有宿主线程名称为空，不根据线程ID猜名称。blocked_reason原始事件存在，但调用地址未符号化，不宣称已取得所有锁或缺页原因。

实际续播位置、稳定条件、返回后视频/音频/服务器资源关闭及活动音轨回收通过。两次模拟器都正常关闭。尚未达到0.8秒，也没有宣布修复完成。
